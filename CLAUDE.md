# family-journey — agent conventions

This repo is the **source of truth** for the Family OS product until v1.0 is implemented: vision, strategy, functional and technical expectations, architectural decisions, and the implementation handoff. Any agent reads this file first. Discovery sessions and scheduled maintenance write here; coding agents only read (see the last section).

## Ground rules
- `main` is truth. A doc is only authoritative once merged and its frontmatter `status` is `accepted`.
- Scoping: one session = one document or one decision. Do not sprawl across unrelated docs in a single session.
- Every doc under `docs/` has YAML frontmatter (see `templates/`). Never strip or hand-edit `INDEX.md`; regenerate it with `python3 scripts/build-index.py`.
- ADRs are immutable once `accepted`. To change a decision, write a new ADR that `supersedes` the old one and flip the old one to `superseded`.
- Prefer short docs that link to each other over long docs. Use relative links and the doc `id` in `depends_on`.
- No PII about family members beyond first names. No credentials, hostnames, or secrets in this repo.

## Commit model
- `main` is protected: every change, docs included, lands by PR. No exceptions for agents or for Mike.
- Branch `draft/<id>-<slug>` for new or revised docs; `chore/<slug>` for scaffolding, templates, scripts. Fill the PR template; Mike reviews and merges from any device.
- `INDEX.md` is regenerated by the `index` workflow on every push to `main`. Never edit or commit it by hand; it is the one thing `github-actions[bot]` may push directly.
- Conventional-commit style subjects: `docs(adr): ADR-0003 event storage`, `chore(templates): add handoff`.

## Dispatch
- `BACKLOG.md` is the parking lot: unshaped one-liners, added from anywhere.
- GitHub issues (`dispatch` template) are the queue: shaped work with a target doc, question, and dependencies.
- "Dispatch: <idea>" promotes a backlog line into an issue and replaces the line with `#N`.
- A session picks up one issue, does the work, and references it in the PR (`Closes #N`).

## Status vocabulary
`draft` → `review` → `accepted` → `superseded` (ADRs) / `retired` (everything else).

## For coding agents (utility node)
Nothing is handed to a coding agent until discovery has ended (`docs/10-strategy/discovery-outcomes.md`). From then on the coding agent reads this repo directly. Nothing is copied into the code repository, so there is one copy of every doc.
1. Start with the handoff document and follow its reading order.
2. Your first deliverable is an implementation plan and roadmap for Mike's approval. Then build one milestone at a time, in the code repository.
3. Do not edit this repo. If a document is ambiguous or contradicts an ADR, stop and ask Mike rather than guessing: open an issue here with the `question` label. Any resulting change to a doc lands here by PR.

Once v1.0 is implemented, the code repository is the source of truth and this repo is a historical record.
